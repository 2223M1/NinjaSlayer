# 遥测压缩与上传修复 — 2026-09-29

基线 `06443d101b34988dca3ec9cb83070e2c5defa194`（0.3.4）。用户提供的 9 月 28 日日志使用 stable 0.107.1、RitsuLib 0.6.2、忍者杀手 0.3.3，正确连接自定义域名，但出现五次 HTTP 413。日志没有请求正文、字节数或接收端错误码，不能据此认定一份单人战报超过了 5 MiB，也不能证明 R2 写入失败。

## 依据与实测

- [RitsuLib v0.6.2 队列](https://github.com/BAKAOLC/STS2-RitsuLib/blob/1bebdb0365c34f8dc9066ded81ac4587df145449/src/Telemetry/Queue/TelemetryQueue.cs)每批取最多 1,000 条，不按字节拆分；原生 PostHog 适配器发送未压缩 JSON。接收端限制为 50 条、5 MiB，失败后整批保留重试。这个不匹配可以独立复现。
- [Spire Codex 对局接口](https://github.com/ptrlrd/spire-codex/blob/69b3c898a1b62fa277359a17970b9061abf60354/backend/app/routers/runs.py)逐局接收，普通 JSON 上限 512 KiB；战报另用 gzip，压缩/展开上限 2/16 MiB。它使用 MongoDB。这里引用的是源码上限，不是 Spire Codex 玩家记录的平均大小。
- 本地四份真实单人 AutoSlay 通关捕获均为 48 层，普通遥测 JSON 约 319–385 KiB，gzip 后约 19–22 KiB，减少约 94%。原生运行历史约 60–63 KiB，其余主要是逐场战斗统计；没有发现完整战报被重复塞入统计。
- `verified-autoplay-combat` 捕获包含 29 场战斗、13,640 个动作。加上 HTTP 信封后，统计 394,752 → 22,629 字节；战报信封 211,063 → 158,486 字节。两类合计传输减少约 70%。战报正文原本已经 gzip，存储压缩体积 157,523 字节。
- 这些是本机实机样本，不是该玩家的原始请求。原始捕获保留在忽略目录，不提交、不上传到生产服务。

## 实现

`NinjaSlayerTelemetryAdapter` 通过公开 `ITelemetryAdapter` 接入，沿用 RitsuLib 授权、持久队列和重试。每次 HTTP 请求只发一条记录并使用 gzip，先发统计，再发公开战报。原队列在新版适配器中同样压缩和拆分，不改旧事件内容。

框架只提供整批确认，因此适配器在本进程保留部分成功记录的身份，下一次原生重试跳过这些记录；队列仍在本地，只有整批成功才由框架移除。进程重启后的重复发送通过确定性 PostHog capture UUID 和现有 R2 回执去重。公开战报被拒绝时仍保留重试资格，日志只增加事件类别、错误码和字节数。

Worker 同时接收旧 JSON 与 gzip。请求在压缩前后都限 5 MiB，保留每批 50 条、每日 25 MiB 展开 JSON 以及战报 2/12 MiB 限额。损坏 gzip 和超限解压明确返回错误。未提高 R2 免费档容量或操作预算。旧版客户端的超大批次需要更新客户端才能拆分补传。

## 验证

- stable 与 preview 产品构建均为零警告、零错误；实际候选 DLL 在两个精确宿主上执行上传契约，覆盖 gzip 内容、逐条发送、部分 429/413、反序列化后的队列重试及整批确认。
- 实际 .NET 请求在 Miniflare 的 Worker、Durable Objects、KV、R2 上端到端通过；PostHog 使用本地 mock。统计内容保持一致，战报可读取，重试复用 UUID 与 R2 回执。
- 上述真实通关捕获在同一本地链路通过，核对全部统计字段；没有向线上统计添加测试对局。
